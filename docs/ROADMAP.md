# Stohn Wallet — Roadmap

Current status, remaining work, and the order to do it in.

| Field | Value |
| --- | --- |
| App version | `0.28.2-fullmode` |
| Platform | Android, `arm64-v8a` only, minSdk 26 / targetSdk 36 |
| Toolchain | AGP 9.4.0, Gradle 9.6.0 (wrapper), JDK 17 |
| Maturity | Pre-release prototype. **Not for real funds.** |

## Guiding constraints

1. The wallet must stay self-contained: local full node, local RPC on loopback, no third-party telemetry or remote signer.
2. Every runtime artifact is hash-pinned and verified before execution. New artifacts require a new pin, never a bypass.
3. Distribution is sideload-first. Bundled PRoot and glibc binaries make store distribution a separate decision, not an assumption.
4. Security work outranks features. A feature that weakens the runtime boundary does not ship.

## What works today

| Area | State |
| --- | --- |
| Embedded runtime | PRoot + loader + libtalloc + libandroid-shmem verified against `RuntimeManifest`; Debian rootfs and Stohn Core 3.2 downloaded, hash-checked, extracted with traversal/symlink/size guards |
| Node lifecycle | Foreground service, single-instance `NodeController`, ephemeral loopback RPC port, cookie auth, restart-after-encrypt |
| Wallet | Create/load wallet, send with fee estimate, transactions list, encrypt passkey, lock wallet |
| Backup | AES-GCM container, PBKDF2-SHA256 600k, zip payload with SHA-256 manifest, atomic writes, restore path validation |
| Import/migration | `wallet.dat` inspect + migrate through the official Core tool inside PRoot |
| QR | Receive QR and share text carry a `stohn:<address>` request, QR shareable as an image; the send-side scanner resolves payloads through the tested `Amounts.parseUri` (`stohn:`, foreign schemes, bare addresses, `amount` and `label`) |
| Address book | Labels in `filesDir/addressbook/labels.json`, saved from the send screen or the searchable address-book screen, shown on send and in transaction detail |
| App lock | Salted PBKDF2 PIN verifier with persisted attempt throttling; gates cold start and return from background after a configurable grace; biometric prompt with device-credential fallback; `FLAG_SECURE` |
| CI | Build job (audit, fullmode verify, unit tests, debug APK) and release job (bundle build, integrate, preflight, sign, verify, upload) |

## Known gaps

- `docs/` is absent from the repository even though `FILES.txt` lists 19 files under it. `FILES.txt` is stale on both sides.
- Unit tests cover amounts, address book, backup crypto, container parsing and the app lock. No instrumented tests, so unlocking on a real device is still unverified.
- The PIN verifier and throttle counters sit in Keystore-backed prefs; a rooted or compromised device can still defeat the lock at runtime, which is why `SECURITY.md` keeps the app in the not-for-real-funds category.
- Release signing secrets are still unset, so the release job builds but skips.

## M0 — App-lock correctness (do first)

Small, self-contained, and the current weak point.

- [x] Replace the unsalted PIN hash with a salted, slow KDF (PBKDF2-HMAC-SHA256, ≥200k iterations, 16-byte random salt) or a Keystore-bound verifier. Store only the verifier. — `PinHasher`, 210k iterations, legacy digest accepted once and upgraded on first correct entry.
- [x] Add attempt throttling: exponential backoff after 5 failures, wipe-after-N option documented. — `PinThrottle` persists the counter and block expiry, so a restart does not reset it; the wipe policy is written down in `SECURITY.md` instead of implemented, because the wallet has no remote channel.
- [x] Require a PIN before biometric unlock can be enabled; disable biometric whenever the PIN is cleared. — enforced in `AppAuthManager`, refused with a toast in Settings.
- [x] Re-lock on background. — decided in `onStart` by the pure `LockGate`; grace is configurable from Settings → Security (immediately / 30 seconds default / 2 minutes) so a system dialog does not bounce the user back to the lock.
- [x] Add `WindowManager.LayoutParams.FLAG_SECURE` to `MainActivity` (and the biometric prompt host) so screenshots and recents previews are blocked.
- [x] Redact notification content for the node service. — `VISIBILITY_SECRET` plus a coarse public version.
- [x] Delete or wire up `WalletKeystore` and `WalletManager`; do not leave unused security code. — both removed, and `tools/security-audit.sh` fails if either reappears.
- [x] Tests: PIN verify/clear, throttling state machine, lock state transitions (JVM where possible). — `PinHasherTest`, `PinThrottleTest`, `LockGateTest`.

**Done when:** cold start and resume both gate on authenticator, a stolen prefs file does not yield a PIN offline in seconds, and no unused security classes remain. **Met.**

## M3 — Node and runtime

- [x] Start/stop controls and sync progress percentage in the node screen (currently status-only). — `NodeController` gained a `STOPPING` status, a stop that remembers the user's choice (`startUnlessStopped`), and `syncPercent`; the pure `SyncProgress` helper turns Core's block/header counters into a whole percent and is unit tested; the node screen shows the bar, the blocks-behind count and Start/Stop, and the home card mirrors the percentage.
- [x] Surface disk usage and pruned-mode option. — the node screen shows chain-data size and free space, and offers full / pruned (550 MiB) / pruned (5.5 GiB); Core only accepts `-prune` on a fresh chain database, so switching stops the node, clears only `blocks`, `chainstate` and `indexes` (never `wallets` or the config) through the tested `NodeStorage` allowlist, and restarts.
- [ ] NDK-native backend to replace PRoot, behind the existing `RuntimeBackend` interface. This is the long-term fix for the glibc/PRoot overhead and the store-policy problem. — **seam landed:** `RuntimeBackend` now carries everything the app needs from a node (RPC, wallet tool, backup snapshot, data dir), `NativeRuntime` implements it for a bionic `stohncoind` shipped as `libstohncoind.so`, and `RuntimeBackendFactory` selects it only when both native binaries match their pins in `RuntimeManifest` — the pins are blank today so PRoot still runs, a malformed pin or a hash mismatch is a hard failure rather than a quiet swap, and `NativeLaunch`/`WalletToolArgs` cover the rules with 16 unit tests. **Still open:** the bionic build itself (`scripts/build-android-core.sh` needs `ANDROID_NDK_HOME`, absent here, plus the source-version-specific dependency patches), and `RuntimeInstaller` still downloads the Debian rootfs even when the native backend would be selected. **Installer half now closed:** `installIfNeeded` takes the factory's own `NativeLaunch.decide` and returns before downloading anything when the backend is `Ready`, so a native build no longer pulls a Debian rootfs it will never run — the installer and the factory can no longer disagree.
- [ ] Runtime update path: new manifest pins shipped together with a signature check, no silent swaps. — **trust half landed:** `SignedRuntimeManifest` is a single atomic file (`filesDir/fullmode/runtime-update/manifest.txt`: canonical payload + final `signature` line), ECDSA P-256 verified **before** the payload is parsed, `stage()` refusing anything not newer than `BUILTIN_MANIFEST_VERSION`, `effective()` throwing on an invalid, oversized or partial staged file rather than silently falling back to built-in pins, `RuntimeBackendFactory` and `RuntimeInstaller` resolving every updatable pin through it, `RELEASE_PUBLIC_KEY` blank so the path stays inert, and 19 unit tests covering tampering, foreign keys, format refusals, rollback and staging. **Transport half landed:** `RuntimeManifestTransport` downloads `RuntimeManifest.MANIFEST_URL` (blank, so no request is made at all), refuses anything but a plain HTTPS URL, follows at most 3 redirects and re-checks each hop for HTTPS instead of letting the platform downgrade silently, bounds the body at the document limit, and hands the bytes to `stage` — the only write path, which verifies first. Transport failures are `Declined`, never fatal and never destructive: offline, 404, oversized, tampered or foreign-key documents leave the staged manifest and the pins in force exactly as they were, while a document that is invalid on disk stays fatal where pins are resolved. `MainActivity` attempts a refresh at start. 15 unit tests. **Still open:** no published endpoint or release key, so the transport is inert in this build and the box stays unchecked until both exist.
- [x] `PROOT_TMP_DIR` / `TMPDIR` cleanup on failure and on app start. — PRoot now gets its own `proot-tmp` scratch directory inside the cache instead of the cache root, so cleanup can be total without touching QR images, staged wallets or backups; the tested `RuntimeTemp` helper prepares it, refuses to purge anything that is not a real child of the cache, and the runtime purges it when a launch or the wallet tool fails, with `MainActivity` collecting the leftovers of a killed process at start whenever no node is running.

## Milestones

| Milestone | Contents | Exit criterion |
| --- | --- | --- |
| **M0** | App-lock correctness | Lock is enforced on start and resume; PIN storage is KDF-hardened |
| **M1** | Wallet UX + amount correctness | No `Double` amounts; confirm/detail screens exist |
| **M2** | Backup v2 + test restore | User can verify a backup restores |
| **M3** | Node UX + native backend | Node controllable from UI; PRoot optional |
| **M4** | Test + CI depth | Instrumented tests and static analysis gate in CI |
| **M5** | Signed, reproducible release | Signed APK from CI with published checksums |
| **M6** | Docs complete | `docs/` restored and `FILES.txt` accurate |

## Explicitly out of scope for now

- Multi-chain support, token/asset layer, or smart contracts.
- Cloud backup, cloud sync, or any remote key custody.
- Desktop or iOS clients.
- On-chain analytics or price feeds.

## Notes on sequencing

M0 is deliberately first: it is days of work, it closes a real weakness, and it does not touch the runtime boundary. M1 and M2 can proceed in parallel once M0 lands. M3's native backend is the largest single item and should not block M1/M2. M5 stays blocked until the M0–M2 items are done and a device matrix has passed, because shipping a signed APK of a prototype invites exactly the misuse `SECURITY.md` warns against.
